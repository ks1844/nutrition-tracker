## 2. ID 体系とトレース

| 接頭辞 | 意味 | 定義場所 | 例 |
|--------|------|----------|----|
| FR-nnn | 機能要件 | [01.要件定義.md §4](01.要件定義.md) | FR-020 |
| NFR-nnn | 非機能要件 | [01.要件定義.md §5](01.要件定義.md) | NFR-001 |
| S-n | 代表シナリオ | [01.要件定義.md §3](01.要件定義.md) | S-2 |
| D-n / Q-n | 決定事項 / 未決事項 | [01.要件定義.md §9](01.要件定義.md) | D-4, Q-2 |
| SCR-nn | 画面 | [08.画面設計.md](08.画面設計.md) | SCR-05 |
| API-nn | API エンドポイント | [09.API仕様.md](09.API仕様.md) | API-12 |
| AC-領域-nnn | 受け入れ基準 | [10.受け入れ基準.md](10.受け入れ基準.md) | AC-CALC-004 |
| ADR-nnnn | 設計判断 | [adr/](adr/) | ADR-0002 |
| DP-n | デプロイの決定事項 | [14.デプロイ設計.md §1](14.デプロイ設計.md) | DP-5 |

トレースの向き: **FR → SCR → API → AC**。

```
FR-021（リアルタイム栄養プレビュー）
  └→ SCR-05（メニュー作成ウィザード ②）
        └→ API-12（POST /api/menus/preview）
              └→ AC-MENU-002 / AC-CALC-004
```

- FR ごとの対応表の正本は [10.受け入れ基準.md §2](10.受け入れ基準.md)。
- 画面側は [08.画面設計.md](08.画面設計.md) の各画面に「関連 FR / API / AC」、API 側は [09.API仕様.md](09.API仕様.md) の各エンドポイントに「関連 FR / SCR / AC」を持つ。
- ID は欠番にしても詰め直さない（外部から参照されるため）。廃止は「廃止」と明記して残す。

## 3. 運用ルール

1. **正本は 1 か所**: 同じ事実を複数文書に書かない。他文書は ID とリンクで参照する（例: 栄養素コードは [04.データモデル.md](04.データモデル.md) が正本）。
2. **暫定値は「暫定」と明記**: 係数・重み・閾値などで根拠が固まっていないものは必ず「暫定」と書く。確証のない公式値（食事摂取基準・成分表の数値）は書かない。
3. **仕様変更は文書が先**: 実装を変える前に該当文書（と AC）を更新し、その後にコードを合わせる。
4. **未決は [01.要件定義.md §9](01.要件定義.md) に集約**: 各文書に TODO を散らさず、Q-n として登録し ID で参照する。
5. **正解データで機械検証**: 栄養計算・スコアの期待値は表形式で書き、そのままテストコード化する（[03.栄養計算仕様.md](03.栄養計算仕様.md)、[06.スコアリング仕様.md](06.スコアリング仕様.md)、[10.受け入れ基準.md](10.受け入れ基準.md) で数値を一致させる）。
6. **公開リポジトリ**: シークレット・個人情報・実在ユーザーのデータを書かない。
