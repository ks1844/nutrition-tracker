# ADR-0005: MVP は固定ユーザー 1 名

- 状態: **仮決定**（D-1。認証導入時期は Q-6）
- 日付: 2026-10-17
- 関連: [01.要件定義.md §9](../01.要件定義.md) / [04.データモデル.md](../04.データモデル.md)

## 状況

本アプリは学習用の個人開発で、利用者は開発者本人のみ。認証・ユーザー管理を MVP に含めると、栄養計算・スコアという主目的に割く時間が減る。一方、将来の複数ユーザー化でスキーマを作り直すのは避けたい。

## 決定

- **MVP は固定ユーザー 1 名**で動かす。認証は導入しない。
- ただし `users` テーブルを作り、ユーザーに紐づくテーブル（`Tユーザープロフィール`, `menus`, `T食事記録`）は最初から `ユーザーID` を持つ。
- 固定ユーザーは V2 マイグレーションで `users` に 1 行（id=1）投入する。API 層で常にそのユーザーに解決する（リクエストにユーザー識別子を含めない）。

## 理由

- 認証を省いても、データモデルを変えずに後から導入できる（`ユーザーID` の解決元を差し替えるだけ）。
- API 仕様もユーザー識別子を持たないため、認証導入時はヘッダー/トークンの追加のみで済む。

## 結果

- 公開してインターネットから到達できる構成にすると、誰でも同じデータを読み書きできる。**公開デプロイ前に認証を導入するか、非公開にする**必要がある。デプロイは**自分の IP のみ許可**して運用する（[14.デプロイ設計.md](../14.デプロイ設計.md) DP-5）ため、認証は導入しない（Q-6 は未決のまま）。
- 食材マスタは全ユーザー共通（`ユーザーID` を持たない）。
- 複数ユーザー時に必要な認可チェック（他人の記録へのアクセス拒否）は未実装。

## 代替案

| 案 | 不採用の理由 |
|----|--------------|
| 最初から認証を導入（Cognito 等） | MVP の主目的に対して工数が大きい。費用も出る可能性（NFR-006） |
| `ユーザーID` を持たない | 将来のスキーマ変更が大きい |
