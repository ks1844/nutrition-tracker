## 1. 方針

| # | 方針 | 理由 |
|---|------|------|
| 1 | 最初に**フロントエンドのプロトタイプ**（Mock API）を作り、画面で動作を確認する。プロトタイプは**捨てずに本開発へ発展**させる | 画面設計の誤りを、バックエンドを作る前に見つける。作り直しを避ける |
| 2 | 次に**バックエンドとテーブル**を作る。**テストコードはバックエンド開発と並行**して書く | 正解データがあり、計算は純粋関数なので、実装と同時にテストできる |
| 3 | 最後に Mock API を実 API に**切り替え**て結線し、E2E で通しを確認する | 画面と API の食い違いを段階的に潰す |
| 4 | デプロイは**後**。EC2 → RDS → デプロイの順に、短期間で作って確認し、すぐ破棄する | 課金を避ける（NFR-006） |
| 5 | **文書が先**。仕様を変える場合は設計書と AC を直してからコードを直す | [README.md](README.md) 運用ルール 3 |

## 6. 各段階の進め方（Git 運用を含む）

### 6.1 進め方

1. 作業ブランチを `dev` から切る。**開発のまとまり**ごとに 1 ブランチ（例: `feature/backend-development`）。
2. 対象の FR/SCR/API/AC を確認し、食い違いがあれば**設計書を先に直す**。
3. **機能を 1 つずつ**実装し、テストを書き、ローカルで動作確認する（DB → バックエンド → フロントの順に起動）。
4. **機能 1 つが終わるたびに、その機能だけをコミットする**（作業ブランチ上。指示は不要）。
5. プッシュ・PR 作成は、指示があったときだけ行う。PR は `dev` へ、**開発のまとまり 1 つにつき 1 つ**。

### 6.2 コミットの粒度

**1 コミット = 1 つの機能（1 つの意図）。** コミット履歴を見れば、どんな機能を追加したかが分かるようにする。

| 方針 | 内容 |
|------|------|
| 単位 | 機能・振る舞いの追加 1 つ。例: メニュー作成 API／メニュー更新 API／メニュー削除 API／マイグレーション V3／栄養量の計算ロジック |
| 含めるもの | 実装 ＋ **テスト** ＋ 関連する設計書の更新を**同じコミット**にする（テストだけ別コミットにしない） |
| 動く状態 | 各コミットで**ビルドとテストが通る**。途中で壊れた状態をコミットしない |
| 混ぜない | 機能追加とリファクタ、整形、依存の更新は別コミット |
| 設計書が先 | 仕様を変えるときの設計書だけの先行変更は、`docs:` の別コミットにしてよい |
| 大きさの目安 | 数ファイル〜十数ファイル程度。大きすぎれば機能をさらに分ける |
| 順序 | 依存の順（土台 → 上位）。例: マイグレーション → ドメインロジック → API → 画面の結線 |
| 直し方 | プッシュ済みのコミットは書き換えない（`--amend`・強制プッシュ禁止）。直すときは `fix:` の新しいコミット |
| メッセージ | **日本語・体言止め**（「〜を追加」。「〜する」で終えない）。`feat:` `fix:` `refactor:` `docs:` `test:` `chore:` の接頭辞。本文に理由と FR / API / AC の ID |

メッセージの例:

```
feat: メニュー更新 API（PUT /api/menus/{id}）を追加

食材量・完成後重量・杯数を更新できるようにする。更新しても過去の記録のスナップショットは変えない。
FR-024 / API-09 / AC-MENU-005, 009
```
